# IA Empleado — Commercial proof and evidence system

The commercial website must distinguish **what a visitor can inspect** from **what still requires implementation or measurement**. Visual polish must never collapse those categories.

## Evidence labels

### DEMONSTRABLE / DEMOSTRABLE
Use only for behavior that a visitor can inspect directly on the public site or Reference Lab experience.

Examples:
- collaboration simulator handoffs;
- visible system and human-control states;
- Team Builder composition logic;
- Process Analyzer before/after representation.

A demonstrable website interaction is **not automatically a production-runtime capability claim**.

### VERIFIED / VERIFICADO
Use only when the result has been checked against an actual implementation, test, production event or other auditable source.

A verified claim should have a traceable source. Do not use this label as decoration.

### MEASURED / MEDIDO
Use only for metrics captured from an actual execution or real operational dataset with a known measurement method and period.

Measured numbers must not be replaced by marketing estimates without changing the label.

### ESTIMATE / ESTIMACIÓN
Use for calculations based on user-provided or example assumptions.

The ROI calculator belongs to this category. It must keep assumptions visible and must not imply guaranteed savings.

### POTENTIAL / POTENCIAL
Use for a plausible benefit of an architecture or workflow design that has not yet been measured in the user's environment.

Examples:
- less operational fragmentation;
- better context continuity;
- clearer traceability;
- reduced manual handoffs.

Potential outcomes must never be presented as guaranteed outcomes.

### INDICATIVE ANALYSIS / ANÁLISIS ORIENTATIVO
Use for design/discovery outputs that help frame a process, team or architecture but still require technical validation.

The Process Analyzer and Team Builder recommendations belong here unless backed by a validated customer implementation.

## Comparison-page rules

Comparison pages are decision aids, not winner tables.

They must:
- preserve the statement that comparison patterns are not universal rules;
- show when IA Empleado fits, when the alternative fits and when combining both makes sense;
- separate demonstrable behavior, indicative analysis and estimates;
- describe unmeasured architectural improvements as **potential**;
- keep human authority and integration quality visible in the decision;
- avoid unsupported superiority, percentage, productivity or ROI claims.

## Visual proof pattern

The approved comparison visual sequence is:

`Before / isolated approach → With IA Empleado → Potential outcome`

The third stage must explicitly carry a **POTENTIAL · NOT GUARANTEED** / **POTENCIAL · NO GARANTIZADO** label until real evidence supports a stronger status.

## Commercial evidence surfaces

Public evidence cards link to three distinct surfaces:

1. **Collaboration simulator — DEMONSTRABLE**  
   Shows handoffs, systems and human-control semantics. It is a public demonstration, not proof of a customer's production runtime.

2. **Process Analyzer — INDICATIVE ANALYSIS**  
   Helps discuss current/proposed workflow responsibility. It requires technical discovery before becoming an implementation proposal.

3. **ROI calculator — ESTIMATE**  
   Builds scenarios from visible assumptions. It is neither a measured metric nor a guaranteed financial outcome.

## Future customer proof

When real customer evidence becomes available, add it through a structured proof record containing at least:
- evidence status;
- source/type;
- date or measurement period;
- metric definition;
- baseline and comparison method when relevant;
- customer/anonymization permission;
- implementation scope;
- caveats and known confounders.

Do not convert a testimonial, demo, synthetic example or model-generated statement into a measured case study.
